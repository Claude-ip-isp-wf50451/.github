<p>团队换人时最常见的两种做法，一种是重建环境求个干净，一种是原样交接只换操作人。哪种更稳，靠争论说不清，不如做一次小规模对照。这篇记录了我们用十个号做的两周实验：A 组交接时重建环境，B 组只换人不动环境，两组都用原生家宽双 ISP 出口，过渡期按量计费。指标和结论都放出来，你自己照着重做一遍也不难。</p>

<h2>一、实验怎么设计：两组各五个号</h2>
<p>参与实验的十个号都是养了四十天以上的成长号，分布在同一城市的两个运营商段上，日常任务量相近，每天三到五次对话加一次后台操作。实验期十四天，交接发生在第二天上午，原操作人退出，接手人此前没用过这批号。</p>

<h3>变量控制：只动一件事</h3>
<p>A 组按新机器、新 profile、新出口重建，时区语言尽量贴近原配置；B 组沿用原有 profile 目录与出口，只更换登录操作人，并在台账里记一笔交接时间。其余条件保持一致：任务脚本、使用时段、每日操作次数都不变。只动一个变量，结论才有意义。</p>

<h3>观测指标与记录方式</h3>
<p>四个指标：额外验证触发次数、首次响应延迟、会话中断次数、异常提示出现次数。记录方式用最笨的办法，一张共享表格，交接人每天下班前填一行，延迟取当天三次测量的中位数。不做自动采集，是为了避免脚本本身影响结果。</p>

<h2>二、A 组：交接时重建环境</h2>
<h3>代价出现在第三天，不在第一天</h3>
<p>重建当天一切正常，登录顺畅，验证也没多。问题从第三天开始：两个号在正常对话中弹出额外验证，一个号的后台出现异地登录提示。原因是重建时时区设对了、语言设对了，但字体列表和 WebGL 渲染器跟原来不是一套，环境整体变成了「一台新设备」。</p>

<h2>三、B 组：只换操作人，环境原样保留</h2>
<h3>双 ISP 出口的切换动作</h3>
<p>B 组用的是原生家宽双 ISP 出口，一条主用、一条备用，同一账号的环境里两条线都预置好，切换在网关侧完成，不动浏览器参数。交接当天把主用线从原操作人的入口解绑，绑到接手人的入口，出口 IP 段不变，只是操作入口变了。这个动作五分钟能做完。</p>

<h3>什么情况下 B 组也会失手</h3>
<p>两种情形：一是接手人的操作习惯差异太大，比如原来每天上午用，接手人改成凌晨集中跑，行为曲线变化比环境变化更明显；二是原环境本身就带着隐患，比如出口段之前被共用过，换人只是把问题推到明面上。所以沿用环境的前提是原环境经过自测，不是「一直没出事所以应该没事」。</p>

<h2>四、结果对比：过渡期尽量不动环境</h2>
<p>十四天跑完，B 组在四个指标上都更好，A 组多花的时间是 B 组的八倍左右，还多付了两次人工处理验证的时间。结论不复杂：换人时优先交接入口，其次交接操作规范，环境能不动就不动。真要重建，等过渡期结束、账号状态稳定之后再单独安排一次，别和交接叠在同一天。</p>

<h3>过渡期的按量计费怎么配合</h3>
<p>交接期通常一到两周，这段时间用按量计费最合适：双 ISP 的备用线只在演练和真掉线时计费，平时不产生支出。按常见报价折算，一条备用住宅线每天只开两小时，两周的额外支出大概几十元，仅供参考。等交接稳定、操作量恢复常态，再把主力线转成包月。</p>

<h3>交接当天必须留下的三样记录</h3>
<p>一是入口变更时间与原操作人退出时间；二是切换前后的出口 IP 与 ASN；三是接手人首次登录的时段与是否触发验证。这三样凑齐，后面出现任何异常都能快速定位是环境问题还是行为问题，不用把两周前的操作重新回忆一遍。</p>

<h2>常见问答</h2>
<h3>交接时把密码和二次验证一起换掉，会影响账号状态吗？</h3>
<p>答：改密码本身是正常操作，建议在熟悉的出口下改，改完当天不要同时做其他变更。密码、出口、设备三项一起动，等于一次给出三个异常信号，风险叠加。</p>

<h3>接手人第一次登录，用原来那个时段还是按自己的时间？</h3>
<p>答：前三天按原时段登录，之后逐步过渡到接手人的正常作息。突然从上午改到凌晨，行为曲线变化比换设备更明显，容易触发额外验证。</p>

<h3>双 ISP 出口的备用线平时要一直开着吗？</h3>
<p>答：不必。按量计费下备用线保持可随时启用的状态即可，每天演练一次切换，确认能在一分钟内接管。长期空跑既费钱也看不出真实切换效果。</p>

<h3>如果原环境本来就不干净，沿用是不是把问题带过去了？</h3>
<p>答：是。沿用环境前先做一轮自测：查归属城市、ASN、时区语言一致性、WebGL 与字体特征。自测不过的号不要交接，先换线再交人，顺序反过来会更麻烦。</p>
